# 남용 방지(판정 사용량 제한) 설계

## 왜
운영 준비 로드맵 3단계(① DB·세션 → ② 로그·이벤트 → **③ 남용 방지** → ④ EC2 배포 → ⑤ 사용량 보기).
OpenAI에는 미리 충전한 5달러뿐이라 "돈이 무한정 나가는 사고"는 OpenAI가 막는다. 진짜 위험은 누군가 스크립트로 두드려
**잔액을 하루 만에 태우면 모든 사용자의 판정이 멈추는 것**이다. 판정 비용이 나가는 길을 기기·IP·전체 단위로 막아, 나쁜 날에도 서비스가 며칠은 버티게 한다.

## 지금 상태와 구멍
- 이미 있는 제한: 질문 200자, 추리 1000자, 한 판 사용 40(질문 1, 추리 5).
- 구멍
  1. 초기화 반복: 40을 다 쓰고 초기화하면 다시 40. 횟수 제한 없음.
  2. 쿠키 버리기: 쿠키 없이 요청하면 새 기기. 기기 한도만으로는 못 막는다.
  3. 동시 요청: 한 판에 질문을 동시에 많이 보내면 판정은 모두 돌고 저장만 한 건 빼고 409. 토큰은 다 쓴다.
  4. 하루 전체 상한 없음.

## 목표 / 하지 않을 것 / 실패로 볼 것
- 목표: 판정(질문·추리) 요청을 AI 서버에 보내기 **전에** 아래 한도로 거절한다. 거절된 요청은 토큰을 쓰지 않는다.
- 하지 않을 것: 캡차, 로그인, 프록시(Caddy) 단 초당 제한(④에서 보조로 검토), 결제·충전 자동화, 관리자 화면(⑤).
- 실패로 볼 것
  - 정상 플레이어(하루 몇 판)가 한도에 걸린다.
  - 서버를 다시 켜거나 배포하면 오늘 쓴 양이 0으로 돌아간다.
  - 한도 검사 때문에 판정이 눈에 띄게 느려진다.
  - 한도에 걸렸을 때 화면이 이유 없이 고장 난 것처럼 보인다.

## 정한 것 (사용자 결정)
| 대상 | 한도 |
|---|---|
| 하루 전체 비용 | **2달러** |
| 기기 하나, 하루 판정 | **200번** |
| IP 하나, 하루 판정 | **600번** |
| 한 판의 동시 판정 | **1건** |
- "하루"는 **한국 시간(Asia/Seoul) 자정** 기준.
- 세는 대상은 판정(질문·추리)만. 힌트·포기·조회·초기화는 막지 않는다.
- 판정이 실패한 요청(`judge_error`, `timeout`, `conflict`)도 센다(토큰을 썼거나 썼을 수 있다).
- 단가는 설정 값. 기본 `gpt-5-mini`: 입력 0.25달러, 캐시 입력 0.025달러, 출력 2달러(100만 토큰당).

## 접근 방식
| 방식 | 내용 | 판단 |
|---|---|---|
| **A. `events`로 세기 (선택)** | 판정 전에 `events`에서 오늘 전체 비용, 기기 판정 수, IP 판정 수를 센다. 동시 판정은 메모리의 "판정 중인 판" 집합으로 막는다. | 2단계 기록이 그대로 기준. 재시작해도 유지. 실패한 판정의 토큰도 이미 들어 있음. 쿼리 3번(색인, 수 ms)은 2~4초 판정에 비해 무시할 만함. 동시 요청 몇 건이 한도를 살짝 넘을 수 있음(몇 원). |
| B. 메모리 카운터(Bucket4j 등) | 서버 메모리에서 센다 | 재시작·배포마다 0이 되고, 토큰 예산은 결국 `events`와 따로 세야 함. |
| C. 프록시(Caddy)에서 막기 | IP별 초당 요청 수 | 토큰 예산·기기 한도 불가. ④에서 보조로. |

사용자가 A를 골랐다. 이유: 막으려는 것이 비용(하루 2달러)이라 토큰을 아는 `events`가 기준이어야 하고, 재시작으로 예산이 초기화되면 안 된다.

## 설계

### 1. IP 기록 (Flyway `V3__events_ip.sql`)
- `events`에 `ip_hash text` 칸과 색인 `events_ip_at_idx (ip_hash, at)`를 더한다.
- **IP 원문은 저장하지 않는다.** `events`는 지우지 않고 쌓이므로, 한도 세기에 필요한 "같은 IP인가"만 알 수 있게
  `HMAC-SHA256(비밀 값, IP)`의 앞 32자(hex)를 남긴다. 비밀 값은 `IP_HASH_SECRET`(배포에서 지정, 로컬 기본값 `dev-only`).
  평범한 SHA-256은 IPv4 전체(약 43억 개)를 대입하면 되돌릴 수 있어서 비밀 값을 섞는다.
- 요청의 IP는 `request.getRemoteAddr()`. `RequestIdFilter`가 요청 ID와 함께 MDC `clientIpHash`에 해시를 넣고, `EventRecorder`가 모든 이벤트에 남긴다. 로그에도 원문 IP를 찍지 않는다.
- 배포에서 Caddy 뒤에 서면 `server.forward-headers-strategy=native`(환경 변수 `SERVER_FORWARD_HEADERS_STRATEGY`)로 `X-Forwarded-For`를 믿게 한다. 지금은 기본값(믿지 않음)으로 두고 `DEVELOPMENT.md`에 적는다. ④에서 켠다.

### 2. 한도 검사 (`UsageLimiter`)
- 판정 직전(`GameService.ask`/`guess`에서 규칙 확인 뒤, AI 서버 호출 전) 이 순서로 검사한다.
  1. **동시 판정:** 이 판이 이미 판정 중이면 거절(409, "이전 판정을 기다리는 중입니다."). 판정이 끝나면(성공·실패 모두) 집합에서 뺀다.
  2. **전체 예산:** 오늘(KST) 판정 이벤트의 비용 합 ≥ 2달러면 거절.
     비용 = `(input − cached) × 입력 단가 + cached × 캐시 단가 + output × 출력 단가`(토큰이 null이면 0).
  3. **기기:** 이 기기의 오늘 판정 이벤트 수 ≥ 200이면 거절.
  4. **IP:** 이 IP의 오늘 판정 이벤트 수 ≥ 600이면 거절.
- "판정 이벤트"는 `type in ('question_asked', 'guess_submitted') and outcome <> 'limited'`.
- 거절하면 `limited` 이벤트를 남긴다(`outcome = 'limited'`, `detail: {reason: budget|device|ip}`, 지표 없음). 숫자 셀 때는 빼지만, 누가 얼마나 막혔는지 운영에서 볼 수 있다. 동시 판정 거절은 이벤트를 남기지 않는다(정상 사용자의 두 번 누르기일 수 있다).
- 검사가 DB 오류로 실패하면 **판정을 막지 않고** 경고 로그만 남긴다(기록 실패가 게임을 깨지 않는다는 2단계 원칙과 같다). 최종 안전망은 OpenAI 잔액이다.

### 3. 응답과 화면
- 전체 예산·기기·IP 한도: **429**, `ProblemDetail`의 `detail`:
  - 예산: "오늘 응시자와의 교신량이 모두 찼습니다. 내일 다시 시도해 주세요."
  - 기기·IP: "오늘 이 단말의 교신 한도를 넘었습니다. 내일 다시 시도해 주세요."
- 프런트는 지금처럼 오류 문구를 입력창 위에 보여 주고, 입력한 글은 남긴다. 429는 다시 불러오기(409 처리)를 하지 않는다.
- **게임 도중 예산이 바닥나면:** 예산 429(응답 본문의 `reason: "budget"`)를 받은 순간 상단 안내도 켠다(처음 불러온 `/api/info`를 기다리지 않는다).
  상단 안내 문구는 예산 429 문구와 같다. 입력창은 막지 않는다(자정이 지나면 새로고침 없이 다시 될 수 있게, 그리고 화면을 단순하게).
- 429의 `ProblemDetail`에는 `reason`(`budget` / `device` / `ip`) 속성을 함께 싣는다.
- `/api/info`에 `budgetExhausted: boolean`을 더해, 예산이 바닥났으면 처음부터 상단 안내를 띄운다(사용한 금액 자체는 공개하지 않는다).
- 오늘 쓴 금액은 판정마다가 아니라 **예산의 50%, 80%, 100%를 처음 넘을 때** 경고 로그 한 줄로 남긴다(같은 날 같은 단계는 한 번만, 메모리 기준이라 재시작하면 다시 한 번 찍힐 수 있다).

### 4. 설정 (`application.yml`, 환경 변수로 덮어쓰기)
```yaml
limits:
  daily-budget-usd: ${LIMIT_DAILY_BUDGET_USD:2.0}
  device-per-day: ${LIMIT_DEVICE_PER_DAY:200}
  ip-per-day: ${LIMIT_IP_PER_DAY:600}
  zone: Asia/Seoul
  price:              # 100만 토큰당 달러
    input: 0.25
    cached-input: 0.025
    output: 2.0
```
- 한도를 0 이하로 두면 그 검사를 끈다(테스트·로컬용).

### 5. 테스트
- 백엔드(Testcontainers): 기기 한도 직전까지 `events`를 넣고 판정 → 200번째는 되고 그다음은 429·판정기 호출 없음·`limited` 이벤트; IP 한도 같은 방식(다른 기기, 같은 IP); 예산(토큰이 큰 이벤트 하나로 2달러 초과) → 429 예산 문구; 어제(KST) 이벤트는 세지 않음; `limited` 이벤트는 세지 않음; 동시 판정(판정 중에 같은 판으로 두 번째 요청 → 409, 판정기 1회); 판정 실패 뒤 집합에서 빠짐(다음 판정 가능); 검사 쿼리 실패 시 판정은 진행; 힌트·포기는 한도와 상관없음; `/api/info.budgetExhausted`; 이벤트에 `ip` 기록.
- 프런트: 429 응답이면 문구가 보이고 입력 글이 남고 다시 불러오기를 하지 않음; `budgetExhausted`면 상단 안내.

## 검토 뒤 정한 것 (설계자 판단)
- IP는 원문 대신 비밀 값을 섞은 해시로 남긴다(1절). 공개 배포 전에 정해야 나중에 쌓인 데이터를 옮기지 않아도 된다. ⑤에서 IP 원문은 볼 수 없다.
- 예산 429를 받으면 그 자리에서 상단 안내를 켜고, 입력창은 막지 않는다(3절).
- 거절(429)할 때도 판정 중 집합에는 넣지 않는다(검사를 통과한 뒤에 넣는다). `limited` 이벤트에도 `text_length`는 남긴다.

## 빌더에게 맡기는 것
- 검사 쿼리를 하나로 묶을지 셋으로 둘지.
- KST 자정 계산 방식(`ZonedDateTime` → `OffsetDateTime`).
- 진행 중 판 집합의 자료구조.
- 경고 로그 단계 기억 방식.
- 커밋 단위와 순서.
