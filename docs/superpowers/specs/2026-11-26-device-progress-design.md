# 기기별 진행 저장 설계

## 왜
배포를 앞두고 게임 진행을 서버 메모리에서 DB로 옮긴다. 지금은 서버를 다시 켜거나 6시간 동안 활동이 없으면 진행이 사라지고,
첫 화면으로 돌아오면 하던 게임을 찾을 길이 없다. 로그인 없이, **같은 기기(브라우저)로 다시 오면 이전 상황이 그대로 있게** 한다.
이 DB는 다음 단계(구조화 로그, 사용량 집계)의 바탕이 된다.

## 사용자가 보는 것
- **메인 페이지**: 시나리오 목록은 그대로. 카드마다 이 기기에서의 상태를 붙인다.
  ```
  [ 일주일 연수 ]     ● 진행 중 (12/40)
  [ 뒷골목의 침묵 ]   ✓ 해결 · 87점
  [ 소년의 주문 ]     ✕ 해결 못 함
  [ 다른 사건 ]         (표시 없음 = 처음)
  ```
- **처음인 시나리오에 들어가면**: 지금처럼 새 게임이 시작된다.
- **진행 중인 시나리오에 들어가면**: 질문, 추리, 열린 힌트, 사용 횟수가 그대로 있는 게임 화면으로 이어진다.
- **결말을 본 시나리오에 들어가면**: 결과 페이지가 뜬다. 해결(SOLVED)과 해결 못 함(FAILED, GAVE_UP)이 똑같이 그렇다.
  결과 페이지에 **초기화** 버튼이 생긴다. 누르면 확인 창을 거쳐 그 판을 지우고 새 게임을 시작한다.

## 목표 / 하지 않을 것 / 실패로 볼 것
- 목표: 서버를 다시 켜도 진행이 남는다. 같은 브라우저로 다시 오면 시나리오별 상태와 기록이 보인다.
- 하지 않을 것: 로그인, 기기 간 이어하기(복구 코드 등), 지난 판 기록 보관, 이벤트 로그와 사용량 집계(2·3단계), 배포(EC2).
- 실패로 볼 것: 진행이 사라진다. 다른 사람이 URL이나 ID로 내 게임을 보거나 이어서 할 수 있다.
- 한계(받아들임): 시크릿 창, 다른 브라우저, 쿠키 삭제는 새 사용자가 된다.

## 접근 방식
| 방식 | 내용 | 판단 |
|---|---|---|
| **A. PostgreSQL + 테이블 분리 (선택)** | `games` + `game_entries`(질문·추리·힌트 한 줄씩), Spring Data JPA, Flyway | 질문 하나가 한 줄 추가. 2·3단계 통계를 같은 DB에서 SQL로 뽑을 수 있다. `Game`을 DB에 맞게 손봐야 한다. |
| B. PostgreSQL + 판 전체를 JSON 한 칸 | `Game`을 거의 그대로 직렬화 | 가장 빠르지만 질문 단위 분석이 불편하고 JSON 구조 변경 시 옛 데이터 처리가 까다롭다. |
| C. SQLite 파일 | DB 서버 없음 | 설치가 쉽지만 Spring 궁합이 덜 매끄럽고, 확장 시 다시 해야 한다. |

사용자가 A를 골랐다. 이유: 다음 단계가 이 DB 위에 올라가므로 처음부터 테이블로 나눠 둔다.

## 정한 것
- **한 기기, 한 시나리오, 한 판.** `(client_id, scenario_slug)`는 유일하다.
- **초기화하면 그 판을 지운다**(항목까지 함께). 지난 판은 남기지 않는다. 통계는 2단계의 이벤트 기록으로 따로 남긴다.
- 해결 못 함(실패·포기)은 해결과 똑같이 결과 페이지와 초기화 버튼을 보여 준다. 표시만 "해결 못 함".
- DB는 PostgreSQL, 접근은 Spring Data JPA, 스키마는 Flyway.

## 설계

### 기기 식별 (쿠키)
- `/api/**` 요청에 쿠키 `sto_client`가 없거나 UUID 형식이 아니면 서버가 새 UUID를 만들어 응답에 심는다.
  `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` 1년. `Secure`는 설정값으로 켠다(`game.cookie-secure`, 기본 false, 배포에서 true).
- 같은 요청 안에서 쓸 수 있게 요청 속성에 client id를 넣는다(필터 또는 인터셉터 + 인자 리졸버). 컨트롤러는 `clientId`를 인자로 받는다.
- 쿠키를 받을 때마다 `Max-Age`를 다시 1년으로 늘린다(자주 오는 사용자가 1년 뒤 끊기지 않게). — 빌더 판단으로 둬도 됨.
- `clients` 테이블은 만들지 않는다. client id는 `games`에만 나온다.

### 테이블 (Flyway `V1__games.sql`)
```
games
  id              uuid PK
  client_id       uuid not null
  scenario_slug   text not null
  status          text not null        -- PLAYING / SOLVED / FAILED / GAVE_UP
  used            int  not null
  seq             int  not null        -- 마지막으로 쓴 순번
  keyword_found   int[] not null       -- 맞힌 핵심 키워드 번호(1부터)
  bonus_found     int[] not null
  version         bigint not null      -- 낙관적 잠금
  created_at, updated_at timestamptz not null
  unique (client_id, scenario_slug)

game_entries
  game_id     uuid FK → games(id) on delete cascade
  seq         int                      -- PK(game_id, seq)
  kind        text not null            -- QUESTION / GUESS / HINT
  no          int                      -- 질문 번호, 힌트 번호 (추리는 null)
  text        text not null            -- 질문문, 추리문, 힌트 본문(열린 순간의 문장)
  answer      text                     -- QUESTION만
  correct     boolean                  -- GUESS만
  closeness   text                     -- GUESS만
  created_at  timestamptz not null
```
배열 칸이 JPA에서 번거로우면 `text`(쉼표 구분)나 별도 테이블로 바꿔도 된다(빌더 판단).

### 도메인
- `Game`의 규칙(한도, 힌트 열림, 점수, 추리 처리)은 그대로 둔다. 바뀌는 것은 상태를 어디서 읽고 쓰는가뿐이다.
- `Game`을 JPA 엔티티로 만들거나, 엔티티와 도메인을 나누고 변환하거나는 빌더 판단. 어느 쪽이든 `synchronized`와 `lastActive`, `touch()`는 빠진다.
- `Game.scenario()`는 저장된 slug로 `ContentRepository`에서 찾아 붙인다.
- `GameStore`의 메모리 맵과 `evictIdle()`(6시간 정리)은 없앤다. `game.idle-ttl` 설정도 지운다.

### 동시 요청
판정(최대 28초)은 트랜잭션 밖에서 한다.
1. 게임을 읽고 진행 가능한지 확인한다(지금의 `requireQuestionAllowed` / `requirePlaying`).
2. 트랜잭션 없이 AI 판정을 부른다.
3. 트랜잭션 안에서 게임을 다시 읽어 결과를 반영하고 저장한다. `version`이 1에서 읽은 것과 다르면 반영하지 않고 409를 돌려준다
   ("다른 창에서 진행이 바뀌었습니다. 새로고침해 주세요.").
힌트, 포기, 초기화도 같은 낙관적 잠금으로 막는다. 같은 기기에서 시작 요청이 동시에 두 번 와서 유일성 제약에 걸리면 이미 있는 판을 돌려준다.

### 시나리오가 바뀌었을 때
- 저장된 slug의 시나리오가 사라졌으면 그 판은 없는 것처럼 다룬다. 목록에 안 보이고, 그 id로 오면 404를 준다. 지우지는 않는다.
- 핵심 키워드나 보너스 수가 줄었으면, 공개할 때 지금 시나리오의 범위를 벗어나는 번호를 무시한다(지금 `addGuess`가 하는 걸러내기와 같다).
- 힌트는 열린 순간의 본문을 `game_entries.text`에 남겨 두므로, 이미 열린 힌트는 시나리오를 고쳐도 그대로 보인다.
  다음에 열릴 힌트는 지금 시나리오에서 가져온다.

### API
기존 경로는 그대로 두고, 모든 `/api/games/**`는 **요청한 기기의 게임만** 다룬다. 남의 게임 id면 404(존재 여부를 알려 주지 않는다).

| 요청 | 바뀌는 점 |
|---|---|
| `POST /api/games {scenario}` | 이 기기에 그 시나리오의 판이 이미 있으면 **새로 만들지 않고 그 판을 돌려준다**(200). 없으면 만든다(201). |
| `GET /api/games` (새로 추가) | 이 기기의 판 목록: `[{id, scenario, status, used, limit, score}]`. 메인 페이지 상태 표시에 쓴다. |
| `DELETE /api/games/{id}` (새로 추가) | 초기화. 판과 항목을 지운다. 204. |
| `GET /api/games/{id}` 외 질문·추리·힌트·포기 | 주인 확인과 낙관적 잠금 409가 더해진다. 응답 모양은 같다. |

### 프런트엔드
- `api.ts`: `myGames()`, `reset(id)`를 더한다. 쿠키는 같은 출처라 `fetch` 그대로 실린다.
- `ScenarioList.tsx`: `scenarios()`와 `myGames()`를 함께 불러 카드에 상태를 붙인다.
  카드를 누르면 지금처럼 `start(slug)`를 부르고, 돌아온 판의 `status`가 `PLAYING`이면 `#/game/{id}`, 아니면 `#/game/{id}/result`로 간다.
  상단의 "미해결 N건"은 이 기기 기준으로 아직 해결하지 않은 수로 바꾼다. — 빌더 판단(문구만 바꿀 수도 있음).
- `ResultPage.tsx`: **초기화** 버튼을 더한다. 기존 `ConfirmDialog`로 "기록이 모두 지워집니다"를 확인받은 뒤
  `reset(id)` → `start(slug)` → `#/game/{새 id}`로 간다.
  게임을 못 찾았을 때 문구 "게임이 만료되었거나 서버가 다시 시작되었습니다."는 "기록을 찾을 수 없습니다."로 바꾼다(GamePage도 같다).
- 상태 표시 문구: 진행 중 `진행 중 (used/limit)`, 해결 `해결 · N점`, 실패·포기 `해결 못 함`. 모양은 지금 카드 디자인(`archive-row`)에 맞춘다.

### 개발 환경
- 저장소 루트에 `compose.yaml`을 두고 `postgres` 하나를 띄운다(포트 5432, 볼륨으로 데이터 유지).
- 백엔드 접속 정보는 환경 변수(`DB_URL`, `DB_USER`, `DB_PASSWORD`)로 받고, 기본값은 로컬 compose에 맞춘다.
- `DEVELOPMENT.md`에 "DB 먼저 켜기(`docker compose up -d`)"와 "게임 진행은 DB에 저장된다"를 반영한다. "백엔드를 다시 켜면 게임이 사라진다"는 문장은 지운다.

### 테스트
- 백엔드 통합 테스트는 Testcontainers의 PostgreSQL로 돌린다(로컬에 Docker 있음).
- 꼭 볼 것: 서버(컨텍스트) 재시작 없이 다시 읽어도 기록이 같다, 다른 쿠키로는 404, 같은 시나리오 시작은 같은 판을 돌려준다,
  초기화 뒤 시작하면 빈 새 판, 판정 중에 다른 요청이 상태를 바꾸면 409, 시나리오의 키워드 수가 줄어도 공개가 깨지지 않는다.
- 프런트: 목록의 상태 표시, 끝난 판을 누르면 결과로 가는 것, 초기화 흐름.

## 검토 뒤 정한 것 (설계자 판단)
- **409를 받으면**: 프런트는 서버가 보낸 문구를 보여 주고 게임을 다시 불러와 화면을 최신 상태로 바꾼다. 입력한 질문 글은 지우지 않는다.
- **시나리오 힌트 수가 늘었을 때**: 다음 동작에서 사용 횟수에 맞는 힌트가 한꺼번에 열린다. 지금 규칙(사용 횟수가 힌트 자리를 넘으면 연다)과 같아서 그대로 둔다.
- **첫 방문에 쿠키 없는 요청이 동시에 오면** 서로 다른 UUID가 심길 수 있다. 아직 판이 없을 때라 문제 삼지 않는다.
- 기존 MockMvc 테스트는 쿠키를 받아 다음 요청에 싣도록 고친다. 의존성으로 Flyway 스타터, PostgreSQL 드라이버, Testcontainers를 더한다.

## 빌더에게 맡기는 것
- `Game` 엔티티/도메인 분리 방식, 배열 칸 매핑 방식.
- 쿠키 처리를 필터로 할지 인터셉터로 할지, 만료 연장 여부.
- "미해결 N건" 문구 처리.
- 커밋 단위와 순서.
