# 고칠 것 목록

2026-11-24 첫 실제 플레이 뒤 정리. 구조는 잘 잡혔고, 세부를 다듬는 단계다.
하나씩 꺼내서 설계(brainstorming) → 계획 → 구현 순서로 진행한다.

## 1. 정답 판정 기준 완화
- **완료(2026-11-24, PR #1)**: 핵심 키워드(필수 용어·인정·불인정·빠졌을 때) 형식으로 바꿨다.
- **문제**: 추리 채점이 너무 깐깐하다. 프롬프트보다는 시나리오의 핵심 포인트(정답 기준)가 문장 단위라서 그렇다.
- **방향**: 핵심 포인트를 "문장 전체를 맞혔는가"가 아니라 "이 키워드(개념)를 담았는가"로 판단하게 바꾼다.
- **손댈 곳**: `scenarios/*.md`의 핵심 포인트 형식, `scenarios/README.md` 규격, `scenario-make` 스킬, `ai/app/prompts.py`의 `GUESS_RULES`.
- **메모**: 5번(보너스 키워드)과 같은 틀로 설계하면 좋다. 핵심 키워드 = 정답 조건, 보너스 키워드 = 추가 점수.

## 2. 진행자(응시자) 연출
- **완료(2026-11-25)**: 오른쪽 기록지를 응시자 무전 수신 화면으로 바꾸고, 답·계시가 깨진 글자에서 맞춰지는 연출을 넣었다. 힌트도 계시로 수신 기록에 들어온다.
- **문제**: 지금은 답이 서류에 찍히는 도장이다. 진행자가 "모든 것을 아는 존재"라는 느낌이 약하다.
- **방향**: 응시자가 계시를 내려 주듯 답이 나타나게 한다. 질문을 받는 쪽도 응시자 느낌이 나게 한다.
- **손댈 곳**: `frontend/src/GamePage.tsx`, `frontend/src/index.css`. 지금의 심문실 콘셉트(서류, 도장)를 어디까지 바꿀지 먼저 정한다.
- **메모**: 미뤄 둔 "추리 결과, 힌트, 해결 문구를 진행자 말투로" 작업도 여기서 같이 한다. 4번(배경 이미지)과 함께 설계하는 게 좋다.

## 3. 점수 시스템
- **완료(2026-11-24)**: 사용 한도 40(질문 1, 추리 5), 힌트 10·20·30과 힌트 받기, 마지막 추리, `100 − 사용 + 보너스×10` 점수. 대표·힌트 이미지는 4번에서 한다.
- **방향**:
  - 적은 질문 수로 풀수록 높은 점수.
  - 힌트는 질문을 일정 횟수 이상 해야 열린다.
  - 대표 이미지, 힌트 이미지를 만들어 넣는다.
- **정할 것**: 점수 계산식(질문 수, 힌트 사용, 오답 추리 수, 보너스), 힌트가 열리는 질문 횟수(시나리오마다 다르게 할지), 점수를 어디에 기록할지(지금은 서버 메모리뿐).
- **메모**: 5번 보너스 점수와 한 계산식으로 묶어야 한다. 이미지는 4번과 같은 방식으로 만든다.

## 4. 이미지와 배경 꾸미기
- **자리만 완료(2026-11-25)**: 배경, 사이트 상징, 기본 표지, 문제별 대표·힌트 그림을 넣을 자리를 만들었다(`DEVELOPMENT.md` 이미지 자리). **그림 만들기는 남음.**
- **방향**: 문제(사건)뿐 아니라 배경에도 이미지를 생성해 넣어 더 멋있게 꾸민다.
- **정할 것**: 이미지 생성 방법(어떤 이미지 모델, 미리 만들어 저장할지 게임 중에 만들지), 그림체, 파일을 어디에 두고 어떻게 시나리오와 연결할지.
- **메모**: 미리 만들어 `scenarios/` 옆에 저장하는 쪽이 비용과 속도 면에서 낫다. 시나리오 표면에 세계관 키워드를 드러내지 않는다는 규칙은 이미지에도 적용해야 한다(진상이 그림으로 새지 않게).

## 5. 보너스 판정
- **완료(2026-11-24, PR #1과 3번)**: 시나리오마다 보너스 키워드 2개, 게임 끝에 맞힌 보너스 공개, 점수에 +10씩.
- **방향**: 정답 외에 범행 동기, 방법 같은 세부를 맞히면 보너스 점수를 준다. 특히 힌트가 공개된 뒤에야 알아낼 수 있는 보너스 키워드를 둔다.
- **손댈 곳**: 시나리오에 보너스 키워드 항목 추가, AI 추리 판정이 보너스 키워드도 확인하도록, 화면에 보너스 결과 표시.
- **메모**: 1번(키워드 기반 정답)과 같은 판정 구조를 쓴다. 3번 점수 계산식에 들어간다.
- **결정(2026-11-24)**: 1번을 할 때 시나리오 형식에 보너스 키워드 칸을 같이 만든다(시나리오당 1~2개). 실제 점수 반영은 3번 점수 시스템 때 한다.

## 묶어서 보면
- **판정 쪽**: 1 + 5. 시나리오 형식을 한 번에 바꾸는 게 좋다(13개 시나리오를 두 번 고치지 않게).
- **점수 쪽**: 3. 1 + 5가 정해진 뒤에 하는 게 좋다.
- **연출 쪽**: 2 + 4. 이미지 생성 방법을 먼저 정해야 한다.

## 그 밖에 남아 있는 것
- 판정 속도: 질문과 추리 채점 모두 `low`(질문 약 3초). `minimal`(약 2초)은 운영 질문 178개 재판정에서 규칙을 잘 따르지 못해 쓰지 않는다(2026-11-27).

## 판정 품질 다음 작업 (2026-11-27 운영 질문 검토에서)
- (완료) 반려, 명제 표시, 판정 근거 DB 저장. 명제 평가가 남았다: 진상 낱말이 명제에 새지 않는지, 부정형 질문이 그대로 옮겨지는지 필요한 질문만 골라 실제 AI로 확인한다.
- **추리 채점 흔들림**: 같은 답안이 판정마다 다르게 채점된다(예: "불가능한 부탁"을 '살려 내라'로 인정했다 안 했다 함).
- **'빠졌을 때' 문구**: 키워드를 아예 안 쓴 경우와 썼지만 틀린 경우를 똑같이 "빠져 있구나"로 안내한다.
- **판정 메모 정리**: 메모의 말을 답의 코드와 하나씩 맞춘다(예 / 아니오 / 일부만 맞다 / 조건이 붙으면 예다 / 상관없음 / 정해지지 않음). 남은 "예로 볼 수 있다", "상관없음" 줄을 고치고 `scenarios/README.md`와 `scenario-make` 스킬에도 반영한다.
- 요청 횟수 제한: 외부에 공개 배포하기 전에 필요하다(Codex 리뷰 1번).
- 같은 게임을 여러 탭에서 열 때 화면 상태가 어긋날 수 있다(Codex 리뷰 2번, 드묾).
